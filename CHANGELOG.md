# Changelog

All notable changes to Brimline are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/).

The version lives in the `VERSION` file. `0.0.0` is the development version: nothing is released. Every other version gets its tag and its GitHub release from the CI, with the notes of its section below.

## [Unreleased]

### Added

- **A switch per provider, and "Do not read".** Settings, Accounts has one switch per provider and a "Do not read" box per account; `brimline providers` lists the providers and `brimline providers enable|disable <name>` turns one on or off. Claude is on, as before; every other provider starts **off**. A provider that is off is not looked for at all (no folder, no file, no Keychain item, no request), and an account marked "Do not read" is never read again and keeps its last numbers, with their age. The app takes the change at its next refresh. This also settles the old question of an account you want left alone.
- **For your agents:** `get_usage` and `best_account` take a `provider` argument (`claude`, `chatgpt`, `gemini`, `grok`, `cursor`; `best_account` defaults to `claude`, so a call without it answers as before). `window` also accepts `day`, `month` and `period`; a window that does not exist for the provider (for example `session` for Grok) answers with a clear error. Every account says its `provider`, its `source` (the exact place of its connection, written from your home folder, `~/.claude-work`) and, when it cannot be read, its `reason`; every limit says its `window_seconds` and `label` when the provider gives them. There is no `brimline best` command: agents use the MCP tool `best_account`.
- **`brimline status --provider <name>`** (and `brimline accounts --provider <name>`) limits the answer to one provider. **`brimline status --live --shape`** prints the shape of each provider's answer: its keys and the type of each value, never a value, to check a format; a key that could be data (an address, an id, a UUID, a number) is written `<key>`.
- **Two new states.** `not_readable` (an account the provider gives no readable limit for, with its `reason`) and `format_changed` (the provider answered with something Brimline does not recognize: "The provider changed its answer: update Brimline."). An answer that is not the expected JSON, or a page, used to count as `unavailable`; it is now `format_changed`, and Brimline waits longer before each new try, as it does for `unavailable`. The cache keeps a fingerprint of the keys of the last answer (SHA-256, no value in it).
- **Safe reading, for the providers to come.** A sign-in file is opened without following a link, and only if it is a regular file of yours, 1 MiB at most. Each reader has a closed list of URLs and nothing else is ever called; no cookie is kept, and none is sent except the cursor.com session cookie that the Cursor reader needs. Every text, percentage and date a provider sends is filtered before it is kept (names of 64 characters among letters, digits, `.`, `_`, `-` and the space; percentages from 0 to 100; plausible reset times).

- **ChatGPT, through Codex.** Turn ChatGPT on (Settings, Accounts, or `brimline providers enable chatgpt`) and Brimline reads the limits Codex shows with `/status`: the 5 hour session, the week (alone on a Pro plan, which has no 5 hour window), any other window with its length, and the limits of a model when Codex has some. It uses the sign-in Codex already keeps in `~/.codex/auth.json` (three fields of it, never the refresh token), asks `chatgpt.com` for the usage with one read-only request, never renews anything and never sends an expired token: a Codex left closed for long shows "Open Codex to refresh the sign-in." A Codex signed in with an API key has no subscription limit to show, and one that keeps its sign-in in the Keychain is not read (Brimline never reads Codex's Keychain item). ChatGPT is off until you turn it on. **Read and checked on 27/10/2026 on a ChatGPT Free account** through Codex (the month at 0 %, a 30 day window, ten identical reads, `auth.json` unchanged, test data rewritten from the real answer); the comparison with OpenAI's usage page is pending, and a paid plan was not tried. See [docs/providers.md](docs/providers.md).
- **Gemini, as a sentence.** Turn Gemini on (Settings, Accounts, or `brimline providers enable gemini`) and, when `~/.gemini` exists, it shows one card that says: "Google does not publish Gemini limits in a form Brimline can read. They are in the Gemini app (Settings, Usage limits) and in Gemini CLI (/stats model)." (and its French version), with no number. Without Antigravity, Brimline only checks that the folder is there: it opens nothing inside it, reads no Keychain item, makes no request and launches no program (with Antigravity, see the next entry). Gemini is off until you turn it on. See [docs/providers.md](docs/providers.md).
- **Gemini, through Antigravity.** Turn Gemini on and, when Google's Antigravity CLI (`agy`) is installed at `~/.local/bin/agy`, Brimline launches its official command `agy --print /usage` and shows the limits it prints: per group of models (Gemini models, the other vendors' models, one model on its own), the 5 hour window and the week, with the share used and the reset time. **This is the one third-party program Brimline launches, and the rule is lifted for Gemini in so many words: Google's program may renew its own sign-in; Brimline neither reads nor writes that sign-in.** The launch is guarded: only that exact path (a link, a file of someone else or one others can write is refused), only a build Brimline has verified (SHA-256 and `--version`), fixed arguments (`--print /usage --sandbox`), a new empty working folder, an environment of three variables, 20 seconds, 64 KiB, one launch at a time and, in the app, one read every 15 minutes at most (`brimline status --live` in the terminal does not write the cache, but reads the app's: it is held to that wait when the app tried less than 15 minutes ago, and launches at once otherwise; making it independent of the cache is a Backlog task); the text is read strictly and anything unexpected is "Antigravity was updated: update Brimline." (`format_changed`), never a number. The text is read as it was seen on Antigravity CLI 1.4.8 (the one verified build, 27/10/2026): four columns separated by tabs, the percentage being what remains, which Brimline turns into the share used. **Another build launches nothing.** **Read and checked on 27/10/2026 on a Google account** (`agy` does not say the plan): the five limits it printed (Gemini Models and Claude and GPT models, 5 hours and week, plus Gemini 4 Argon, week) match what Brimline shows, to 5 seconds on the reset times; the percentage was seen live at 100 % remaining only (other values are covered by the tests), the reference is the text of `agy` itself and not Antigravity's usage page, and a paid plan was not tried. Without Antigravity, the sentence stays. See [docs/providers.md](docs/providers.md) and [SECURITY.md](SECURITY.md).
- **Grok, through the Grok CLI.** Turn Grok on (Settings, Accounts, or `brimline providers enable grok`) and, when `~/.grok` exists, Brimline reads the credits the Grok CLI shows: one limit for the current period (a week or a month, named by its length, there is no 5 hour window), with its percentage and its reset time. It uses the sign-in the CLI already keeps in `~/.grok/auth.json` (the session of an xAI account only, four fields of it, never the refresh token, an API key or another issuer's sign-in), asks `cli-chat-proxy.grok.com` for the billing with one read-only request, never renews anything and never sends an expired token: a Grok CLI left closed for long shows "Open the Grok CLI to refresh the sign-in." A free account, whose answer gives no credit limit, says "xAI returns no credit limit for this account." (no cause given, no number promised, never a 0 %); an allowance with no use yet says "No number yet for this period."; and "This limit is a pool shared by the Grok products." for an account on unified billing. A CLI signed in with an API key has no subscription limit to show, and without the Grok CLI xAI publishes no limit ("xAI only publishes Grok limits for the Grok CLI. Without it, they are in your Grok account settings."). Grok is off until you turn it on. Tried on 27/10/2026 on a free account only, its test data rewritten from that answer; **read and checked for that sentence only**: xAI returns no credit limit for a free account, so Brimline shows no percentage, and there is no xAI page or command to compare with. What a paid account (SuperGrok, X Premium Plus) answers was not tried, and nothing is claimed for it. See [docs/providers.md](docs/providers.md).
- **Cursor, through the sign-in of its app.** Turn Cursor on (Settings, Accounts, or `brimline providers enable cursor`) and Brimline looks at Cursor's own state database, `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb`, to see how Cursor keeps its sign-in. When that sign-in is a plain token, Brimline asks cursor.com for the usage of your plan (`GET https://cursor.com/api/usage-summary`, the call the dashboard makes) and shows the cycle as one **Month** limit with its percentage and its reset time, the plan name (`pro`) in its label, and the **Auto** and **API** pools when Cursor gives them. A plan with no number yet says "No number yet for this period." (never a 0 %), and a plan with no cap says "Cursor sets no limit for this plan.". When Cursor protects its sign-in (encrypts it with its Keychain item, or none is there), the card says: "Cursor protects its sign-in on this Mac: Brimline does not read it. Usage is on cursor.com, Dashboard, Usage." (and its French version); Brimline never reads that Keychain item. An expired or refused sign-in says "Open Cursor to refresh the sign-in." and is never renewed. **The request carries the web session cookie of cursor.com** (`WorkosCursorSessionToken`), which is worth more than a read of the usage: it goes to that one address over HTTPS and nowhere else, a redirection is never followed, and the token is used only if its `sub` is a plain identifier and it is not expired. Brimline opens the database read-only, without following a link, one query, and creates nothing in Cursor's folder: it reads the journal mode in the file header first; in the classic mode (the one VS Code uses, so most likely Cursor's) it reads the database whether Cursor runs or not, and waits ("busy") when a `-journal` file shows a write in progress; in WAL mode only while Cursor is running (its `-wal` and `-shm` files exist), and with Cursor closed the card says the same sentence. Cursor is off until you turn it on. **Read and checked on 27/10/2026 on a Cursor Free account** (the token was in plain text; the month, Auto and API at 0 %, ten identical reads, nothing created in Cursor's folder, test data rewritten from the real answer); the comparison with the cursor.com usage page is pending, and a paid plan was not tried. The plan name (`free`, `pro`) is the label of the Month limit in the JSON for agents; neither the text nor the panel shows it. See [docs/providers.md](docs/providers.md).

- **Documentation and pictures for five providers.** The README (English and French) gets a table of the five providers with, for each, how it is read, whether the source is documented, the plan it was tried on (27/10/2026) and its state: nothing is claimed for a plan that was not tried; a free Grok account gets no limit from xAI and Brimline says so. [docs/providers.md](docs/providers.md) opens with the same table and gives the state of each check; [docs/agents.md](docs/agents.md) has an example with two providers whose numbers are checked by a test; [SECURITY.md](SECURITY.md) opens with a table of every place Brimline looks at and the one program it launches; the FAQ, [docs/why.md](docs/why.md) and the guide to linking accounts ("Connecting another provider", English and French, with the "Don't read this account" rule) are read again against the code. The pictures in `docs/images/` are drawn again by `swift run brimline-snapshots`, with Gemini read through Antigravity and a Grok card that says xAI returns no limit; they use invented numbers and carry neither an address nor a plan for the providers that do not keep them.
- **Several Claude accounts, documented and tested.** [docs/accounts.md](docs/accounts.md) (and its French version) gets a "Several accounts" section: a table of how each provider tells its accounts apart, how to have four Claude accounts (one Claude Code folder each), why an account you no longer use stays "Session expired", and that a token made with `claude setup-token` is not read (tried on 27/10/2026 with three such tokens: none returned limits, one HTTP 403 and two HTTP 429; nothing is claimed beyond that). A new test finds four Claude folders in a stable order with four distinct Keychain items. No new source is read: Brimline still reads Claude Code folders only.
- **Claude Code reports: Claude accounts with no folder on this Mac.** `brimline report claude --account <address|auto> [--statusline]` reads what Claude Code already prints about its own limits, on its standard input: the JSON of a status line (`rate_limits`, documented by Claude Code) or the `rate_limit_event` lines of `claude -p --output-format stream-json`. It keeps only the share used and the reset time of the 5 hour session and of the week, in one report per address (`~/Library/Application Support/Brimline/claude-reports/`, folder `0700`, files `0600`, written atomically), and the app shows that account. No token is read, no request is sent, no quota is spent. Window by window, the number of the last input received replaces the one kept and a missing week stays as last seen; a reset that has passed counts as 0 %; a week never seen says "Week: not seen yet in Claude Code's reports", never "no weekly limit"; every card read from a report says its age ("Claude Code report, 3 min ago"). An account with a folder keeps its direct reading and uses its report only when its session has expired or its Keychain item is missing, and only if the report is newer. With `--statusline` the command prints one short line (`5 h 23% · Week 41%`) when its input gave limits, else nothing, and never makes the status line fail, so it can go into an existing status line ([how](docs/accounts.md#claude-code-reports-an-account-brimline-cannot-read-directly)). The command reads its input to its end whatever happens (so `claude -p` never finds its pipe closed), in blocks, a line over 64 KiB dropped as it comes; `--dir` refuses a folder open to other users and never changes one. `--account auto` takes the address of the `CLAUDE_CONFIG_DIR` folder the command sees (or `~/.claude`) and, in a status line, writes nothing when the session's `transcript_path` lies in another folder; in a pipe, give the address. Settings, Accounts has a "Claude Code reports" block with the command to copy for each Claude account, its address filled in, and the `auto` shortcut; "Don't read this account" keeps the report of the account's address unopened, by address (it holds when the folder's `.claude.json` loses the address for a while), and the command keeps writing until it is taken out of the status line. For agents, an account known by its report only has `"source": "report"`, and every account has `observed_at` (null unless its numbers come from a report). The percentage of `rate_limit_event` is in a field that is not in the event's published type (`unifiedWindows`): if it goes, Brimline says "format changed" and shows no new number. See [SECURITY.md](SECURITY.md).
- **The panel and the settings for several providers.** The menu bar window groups the cards by provider (the provider's name, "ChatGPT via Codex"), in a stable order: Claude, ChatGPT, Grok, Cursor, then Gemini. Windows of every kind have a name (`5 h session`, `Week`, `Month`, `30-day period`, Grok's `Credits · week`) and a limit of one model is a compact line under its window (`5 h · codex-mini`, `Week · Fable`), its reset time written only when it differs from the line above; past 6 days a reset says its date ("resets in 12 d (Sun Nov 8)"). An account that gives no limit shows its sentence (the first one, then "Learn more") and no gauge; an account marked "Don't read this account" shows its last numbers in grey and says "Reading turned off in Settings"; a provider that is on but has no account on the Mac says what to do. The glyph follows the closest limit among all providers on, up-to-date accounts first, and VoiceOver says whose number it is. While only Claude is on, a card says once that other providers exist (dismissable). Settings, Accounts has one block per provider (name, switch, what it reads and where it asks, then its accounts) and an **Add a Codex folder…** button. The colors are Brimline's own, not the providers' brands, and no provider's logo is used.
- **Settings, Menu Bar: "Tidy up the menu bar" (QUOTA-73).** Brimline cannot remove the icons of Claude, ChatGPT and Cursor from the menu bar: macOS has no public way for an app to touch another app's menu bar item, and the non-public ways (Accessibility, Screen Recording) are broken on macOS 27. So a fifth tab of Settings, between General and Agents, says where to do it. For each of the three apps that is installed (found by its bundle identifier, listed in the order of the providers) it gives the name of its own switch ("Turn off “Menu bar”" for Claude, "Show in menu bar" for ChatGPT, "Menu Bar Icon" for Cursor, which is in English in both languages), where it is in the app, and an "Open" button; the app's own icon, as macOS shows it, is drawn beside it and never copied. A button opens System Settings on Menu Bar (`x-apple.systempreferences:com.apple.ControlCenter-Settings.extension`, an address Apple does not document, **tried on macOS 27.0.1 on 28/10/2026: it opens the Menu Bar page**; if macOS refuses it, System Settings opens on its home page and a note says to choose Menu Bar), and the Command-drag gesture is explained in three steps. **No permission is asked and nothing of these apps is read but where they are installed** (not their settings, not the Control Center's list). If an app was moved or deleted, a note says it did not open. The names of the switches were read in the installed apps on 27/10/2026 and change with their versions.
- **Settings, Menu Bar: "Hide without removing" (QUOTA-73), off by default.** Turned on, Brimline adds one item of its own to the menu bar, a thin vertical bar (saved by macOS under the name `brimline-separator`); when it is off, there is no bar. Drag once, with Command held down, the icons to hide (Claude, ChatGPT, Cursor, Gemini) to the left of that bar; then **"Hide the icons"** in the Brimline window (and in Settings) makes Brimline's bar long, which pushes them out of sight, and **"Show the hidden icons"** gives the bar its normal length back. The length is 45 % of the narrowest screen on macOS 27 and later (the formula of Hidden Bar before), computed again when the screens change; hiding is refused, icons shown, with a note, when the bar is too far right to hide reliably, when Brimline's own icon is left of the bar, or when the bar's place cannot be read. **Brimline stays right of its bar, so it and its button are never hidden**; turning the setting off, quitting, a crash, or opening the app again always shows every icon, and each launch starts with them shown. **No permission is asked, no private API is used, and no file of macOS or of another app is written** (macOS keeps the bar's place itself). **Apple does not document this technique: it was tried on macOS 27.0.1 on a 1920 pt screen without a notch only, not on a MacBook with a notch nor with several screens.** Guide, in English and French: [docs/menu-bar.md](docs/menu-bar.md).

- **The core of the per-account gauge and of the account colors (first step).** The rules the menu bar and the panel will draw (the next steps of this release): the gauge is one part per account that has a number (its tightest limit now, divided by the number of those accounts, so the whole is their average and never goes over 100 %; an account whose sign-in is missing, refused or not readable is left out even when it keeps old numbers, as in the choice of the best account), with an alert from 90 % whatever the average is, accounts with no number named apart, and a last known value marked as such; each account gets one of ten colors the first time it is seen and keeps it (`accountColors` in `settings.json`, read one by one: a value that is not valid is ignored, a file from 0.2.0 reads as before); contrast (WCAG 2.2) and CIEDE2000 checks for the palette and for a free color; and the VoiceOver sentence of the gauge, in English and French.

- **A color for each account, in the panel and in the settings (QUOTA-72).** Every account has a round dot of its color before its name in the menu bar window (a card that holds a sentence only, like Gemini's, now has its title and its dot too), and **Settings, Accounts** has a **Color** line under each account: the ten colors of the palette (violet, blue, magenta, olive, ink, pine, gold, navy, cocoa, lilac), **Other color…** (the system color picker, without opacity, kept as six sRGB digits and served in the light and in the dark appearance alike), and **Reset to default**, which gives back the color the rule gives now (greyed, with "Default color", when nothing was changed). The first account of a provider has its provider's color, the next ones the first free color; a color is given once and kept (`accountColors` in `settings.json`), so it does not move when another account appears. Two warnings, never a refusal: a color close to another visible account's ("Close to Asso's color: their two shares are hard to tell apart in the gauge.", shown on both accounts, CIEDE2000 under 10 in light or in dark) and a free color too pale or too dark for the gauge's track ("Hard to see in light mode: 1.1:1 contrast on the gauge, 3:1 recommended."). The line is one group for VoiceOver ("Color of Asso", one choice per color, each named) and each color is a button the keyboard reaches. The group headings of the panel and of the settings lose their provider dot, so that a color means one thing: an account. The limit gauges of the panel keep their threshold colors. See [docs/accounts.md](docs/accounts.md).

- **The menu bar shows who consumes: the glyph lies down and becomes a gauge in colors.** One part per account that has a number, packed to the left in the panel's order, in the color of its account (the average of the accounts fills the gauge, never more than 100 %); the limit line at its end becomes a red "!" from 90 % on one account, whatever the average is; a last known value is dimmed; a part that is not empty is at least one pixel; the element is 50 to 74 pt wide (80 at most) and 18 pt high, drawn on the pixel grid at 1x and 2x, with the colors of the bar's real appearance (a dark bar on a Mac in light mode gets the dark values). With no counted account, the upright glyph stays, as a template image. The percentage next to it, when the setting is on, is the most loaded account's; the tooltip gives the average and the alerts, and VoiceOver reads one sentence, the alert first. The element is a colored image, so it is no longer a template image the system tints: a change on purpose to Apple's advice for menu bar icons, written in `design/DA.md`. Pictures: `docs/images/menubar-gauge-light.png` and `-dark.png`.

### Changed

- **`brimline status` says what the panel says (real try of 27/10/2026).** A card is titled like the panel (`ChatGPT`, `Grok`, `Cursor`, never the name of a folder or a file such as `.codex` or `auth.json`; with several accounts of one provider, the place of each connection follows), and Cursor's pools of a month read `Month · Auto` and `Month · API` instead of `Week`.
- **The cache is now version 2.** Limits of more kinds, `source` and `reason` in each account. A cache written by an earlier version is not read: the app writes a new one at its first refresh, and an agent that started before the update answers "no data yet" until `brimline mcp` is restarted (restart your agent's MCP server, or the agent itself).
- **The JSON for agents changes a little.** `kind` is `model` (it was `weekly_model`) for the limit of one model; `folder` is only there for Claude accounts (null for the others), `source` is there for all; `schema_version` is 2.

- **Sightglass is now Brimline.** The app, the `brimline` command and the MCP server (`brimline mcp`, server name `brimline`) carry the new name everywhere: the interface in English and French, the bundle (`Brimline.app`, `eu.thanaelfontaine.brimline`), the "Open at login" LaunchAgent (`eu.thanaelfontaine.brimline.plist`), the folder `~/Library/Application Support/Brimline/`, the `User-Agent` (`Brimline/<version>`), the `BRIMLINE_LANG` variable and the repository address. There is no `sightglass` alias: the app was never published and nothing known calls the old command.
- **Why.** The name Sightglass is already carried by close software: an AI company bought by Juniper Square in April 2026, two GitHub repositories on the same ground (a Claude Code limits tool and a macOS menu bar app) and a product studio, plus trademarks in the United States. A search for Brimline found no software, repository or trademark (TMview, USPTO, WIPO). The rename came before the first public release so that nobody has to follow it later.
- **Your data comes along.** At its first launch, Brimline copies `settings.json` and `usage.json` from `~/Library/Application Support/Sightglass/`: only those two files, never over a file Brimline already has, without following a link, and without changing the old folder. Nothing is deleted.
- **`scripts/install.sh` handles the old install.** It quits the old app (by its full path), removes the old `~/.local/bin/sightglass` link when it points into the old app, turns off the old LaunchAgent (`launchctl disable`, undone by `enable`, the file stays) and writes the Brimline one, then prints the commands that move the old files to the Trash, without running them.
- **Texts, docs and screenshots follow the name.** Both READMEs (with their "Formerly Sightglass" line and the reason), the docs, the design notes and the screenshots in `docs/images/` (rendered again with `swift run brimline-snapshots`) say Brimline.
- **A new icon and a new menu bar glyph.** The app icon and the glyph in the menu bar are redrawn to go with the name: an open tank and, above its rim, a free line, the limit. The liquid rises toward the rim, and the line above it is the limit you are heading for; the vertical level you already knew stays, and it is not mistaken for a battery. The glyph shows the same levels as before: at least one line of liquid as soon as the level is above 0, the full travel only at 100 %, and dimmed (opacity 0.45) when the numbers are expired. The icon has a simpler drawing for 16 and 32 px (thicker strokes, no reflection or glow). `design/` (the sources of the icon, the glyph and the board `planche.html`) and the screenshots in `docs/images/` are rendered again; the colors do not change.
- **The text check keeps the old name out.** `scripts/check_text.py` now refuses the old name, in a text or in a file name, outside this changelog, the dated documents, the migration code and the installer, and the lines that say "Formerly" or "Anciennement".
- **For your agents:** register the server again under the new name, `claude mcp add --scope user brimline -- ~/.local/bin/brimline mcp` (see [docs/agents.md](docs/agents.md)).

## [0.1.0] - 2026-10-25

First version, private: the repository and the site are not public yet. The full notes are in [docs/releases/v0.1.0.md](https://github.com/ThanaelFontaine/Sightglass/blob/v0.1.0/docs/releases/v0.1.0.md).

### What does not work yet

- ChatGPT, Gemini and Grok are not supported: only Claude accounts are read.
- Only the Mac mini has been used: the MacBook Pro and macOS 14 (Sonoma) are not tried yet.
- The usage endpoint is not documented by Anthropic: it may change or stop answering without notice, and Sightglass says so in words when it does.

### Added

- Repository set up: license (PolyForm Shield 1.0.0), contributing guide, security policy, text checks and the release workflow.
- **Menu bar app** (macOS 14 or later): a level glyph that follows the account closest to a limit, with an optional percentage next to it. Its window shows one card per Claude account, named by its email address (or a label you choose), with the five hour session, the week across all models and the week per model, each with its percentage in text and its reset time ("resets in 2 h 10 (14:30)"). Plans without a weekly limit across all models say so in a sentence.
- **Every state in words**: data getting old ("Data from ... ago"), session expired (last known values greyed, nothing renewed), sign-in refused, provider unavailable (reason and time of the next try), not signed in, limit reached.
- **Account discovery**: `~/.claude` and every `~/.claude-*` folder with a `.claude.json`, plus folders added by hand. Each sign-in is read from the macOS Keychain with `/usr/bin/security`, by its exact service name (the hash of the folder's path, as Claude Code names it); nothing is enumerated, renewed or written.
- **Refresh** every 2, 5, 10 or 15 minutes (5 by default) and on demand, with a growing wait after a failure (2, 4, 8, 16, 32 then 60 minutes) and the provider's `Retry-After` honored.
- **Settings window** with four tabs: Accounts (show or hide, label, add or remove a folder, search again, a link to the guide), General (refresh interval, percentage in the menu bar, open at login through a LaunchAgent), Agents (ready to copy command, MCP snippets and cache path), About. It opens in front, from the window or by opening the app again.
- **English and French**, following the language of the Mac (`SIGHTGLASS_LANG` overrides it).
- **`sightglass` command**: `status [--json] [--live]`, `accounts [--json]`, `mcp`, `--version`. The JSON says the age of every number and writes every key, `null` when unknown.
- **Local MCP server** (`sightglass mcp`, stdio, protocol 2025-06-18, also 2025-03-26 and 2024-11-05): tools `list_accounts`, `get_usage` and `best_account` (the account with the most room left, for a window and optionally a model), with text and `structuredContent` answers. The command and the server read the app's cache and never see a token; only `sightglass status --live` reads the Keychain, like the app.
- **Cache and settings** in `~/Library/Application Support/Sightglass/`, readable by your user only; the cache type has no field for a token, and a test checks the written file.
- **Design**: colors, glyph and app icon (`design/`), light and dark mode, never color alone.
- **Scripts**: `scripts/build_app.sh` builds and signs `build/Sightglass.app` ad hoc with the Command Line Tools alone (the command ships inside, in `Contents/Helpers`); `scripts/install.sh` copies it to `~/Applications`, links `~/.local/bin/sightglass` and opens it; `--login` also turns on Open at login.
- **Screenshots** rendered from fictitious data (`swift run sightglass-snapshots`) in `docs/images/`.
- **Documentation**: linking accounts (English and French), installing, agents (command, JSON format, MCP), FAQ, and an honest section on Anthropic's terms for OAuth tokens; README updated.
- **Honest User-Agent**: requests to Anthropic announce `Sightglass/<version>`, never Claude Code.
- Percentages follow the language: "72%" in English, "72 %" in French. The guide link opens the French guide when the app is in French. `best_account` puts unavailable accounts last and never gives 100% room to an account that lacks the limit asked for.
- The Keychain read is stopped after 60 seconds if `security` never answers, so refreshing never stays stuck.
- **Tests**: Swift Testing suites for discovery, Keychain service names, credential and usage parsing (anonymized real answers), service states and backoff, cache, ranking, time formatting and the MCP server. The CI now also runs `swift build`, `swift test` and `scripts/build_app.sh`.

### Security

- Hardening of what Sightglass reads and writes: redirects from the usage request are refused, its body is limited to 256 KiB, an MCP message is limited to 1 MiB per line (longer ones are dropped and answered with an error), and the cache and settings are written through a temporary file created in 0600 inside a 0700 folder.
