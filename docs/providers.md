# Providers

What Brimline reads for each provider, where the source comes from, and what it says when there is nothing it can read. Claude is on by default; every other provider is **off until you turn it on** (Settings, Accounts, or `brimline providers enable <name>`).

**Documented** means described by the provider's official documentation (with a link). **Not documented** means seen in the code of the provider's own client: it can change without notice.

## The five providers at a glance

Every provider was tried on **27 October 2026**, on the account of the maker of Brimline, and **only on the plan named below**. Nothing is claimed for a plan that was not tried (a paid plan in particular). "Read and checked" means: the real answer was read, its shape matches the test data, ten reads in a row gave the same numbers with no change to the provider's files, nothing was written or renewed, and turning the provider off stopped every read. The details of each try are in the section of the provider.

| Provider | What Brimline reads | Source | Plan tried (27/10/2026) | State |
|---|---|---|---|---|
| Claude | The Claude Code sign-in (Keychain), one request to Anthropic | Not documented | Real accounts, since v0.1.0 | Read and checked |
| ChatGPT, through Codex | `~/.codex/auth.json`, one request to `chatgpt.com` | Not documented (Codex's public code) | ChatGPT Free, through Codex: the month at 0 % (a 30 day window) | Read and checked on that plan; **comparison with OpenAI's usage page pending** |
| Gemini, through Antigravity | The text of `agy --print /usage` (Brimline launches Google's program) | The command is documented, the format of its text is not | A Google account, through Antigravity CLI 1.4.8 (`agy` does not say the plan): five limits, none used | Read and checked, with two limits stated below: the percentage was seen live at 100 % remaining only, and the reference is the text of `agy` itself |

## Claude

Read from the Claude Code sign-in in the macOS Keychain, with one request to `https://api.anthropic.com/api/oauth/usage` (not documented by Anthropic). See [Linking your accounts](accounts.md) and [SECURITY.md](../SECURITY.md).

## ChatGPT, through Codex

- **What Brimline reads.** Codex's own sign-in file, `~/.codex/auth.json` (Codex keeps it there, in plain text, by default: [OpenAI's authentication page](https://learn.chatgpt.com/docs/auth)), and nothing else of Codex: no `config.toml`, no Keychain item, and no program is launched. Of that file only three fields are decoded: `auth_mode`, `tokens.access_token` and `tokens.account_id`. The refresh token, the id token and an API key in the same file are never decoded. A Codex folder somewhere else (`CODEX_HOME`) is added by hand, never read from the environment: with **Add a Codex folder…** in Settings, Accounts (it is kept in `settings.json`, `extraCodexFolders`).
- **The one request.** `GET https://chatgpt.com/backend-api/wham/usage` with the access token (`Authorization: Bearer`) and the account id (`ChatGPT-Account-Id`), the call Codex itself makes for its limits. **Not documented** by OpenAI: Codex's public code is the source ([openai/codex](https://github.com/openai/codex), commit `aeb6b22c8bda5f4d4b6ab80ebd3ccdb3f47fb3ab`: `codex-rs/backend-client/src/client/rate_limit_resets.rs` for the call, `codex-rs/codex-backend-openapi-models/src/models/` for the answer, `codex-rs/login/src/auth/storage.rs` and `token_data.rs` for the file). The same limits are **documented** on OpenAI's side, but only through `codex app-server` (`account/rateLimits/read`, [documentation](https://learn.chatgpt.com/docs/app-server)) and `/status` in Codex ([documentation](https://learn.chatgpt.com/docs/pricing)): they are what to compare Brimline with, not what Brimline calls, because `app-server` is a program that renews and rewrites Codex's sign-in, and its page does not allow it for a commercial service.
- **What you see.** A window is named by its length: 18000 seconds is the 5 hour session, 604800 the week, anything else a period with its length (a free plan was seen with 30 days). A plan with no 5 hour window (OpenAI documents that Pro has none) shows the week only. Limits of one model or feature (`additional_rate_limits`) show as that model's limits, with the window length in the name when it is not a week. Each has its percentage and its reset time. Credits and spend controls in the answer are ignored.
- **Never.** An expired access token (read from the `exp` of the token, without checking its signature, with a 60 second margin) is never sent and never renewed: Codex renews it itself when it runs, so a Codex left closed for a long time shows "Open Codex to refresh the sign-in." / "Ouvrez Codex pour rafraîchir la connexion." The card is titled ChatGPT (with several Codex folders, its folder is written under it): the address and the plan from the answer are not kept.
- **When there is nothing to read** (`not_readable`, in the app, in `brimline status` and in the JSON for agents):
  - Codex is signed in with an API key (`auth_mode` is `apikey`), reason `api_key`: "Codex is signed in with an API key: there is no subscription limit to show." / "Codex est connecté par une clé d'API : il n'a pas de limite d'abonnement à montrer."
  - `~/.codex` has no `auth.json` (Codex keeps its sign-in in the Keychain, or is signed out), reason `keychain_or_signed_out`: "Codex keeps its sign-in in the Keychain or is signed out: Brimline only reads ~/.codex/auth.json." / "Codex range sa connexion dans le Trousseau ou n'est pas connecté : Brimline ne lit que ~/.codex/auth.json." Brimline never reads a Keychain item of Codex.
  - The limits of ChatGPT conversations outside Codex have no source: OpenAI does not publish them in a readable form.
- **Other states.** The sign-in file cut short (Codex is rewriting it) is a passing failure that Brimline tries again, never "signed out"; a link, a file of someone else or one larger than 1 MiB is refused; a 401 asks to sign in again; a 429 waits as long as the provider asks, one hour at most; an answer that is not the expected one (another JSON, a page) is "format changed", never a number.
- **State of the check.** The reader was written on data built from the public code of Codex CLI, then **tried on 27/10/2026 on a ChatGPT Free account through Codex** (its `~/.codex/auth.json`): the month at 0 %, a window of 30 days (2 592 000 seconds), status `ok`, ten reads in a row with the same answer, the checksum of `auth.json` the same before and after, `get_usage` carrying no token, and ChatGPT turned off then on again without trouble. The test data were rewritten from the skeleton of that real answer (`brimline status --live --shape --provider chatgpt`, keys only, invented values). **Not compared yet** with OpenAI's own usage page: it needs a signed-in browser session, and the comparison is pending. A paid plan (Plus, Pro) was not tried, and nothing is claimed for it.

## Cursor

- **What Brimline reads.** Cursor's own state database, `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb` (the SQLite file every VS Code based app keeps, [CodexBar](https://github.com/steipete/CodexBar), commit `5f93dc3`, `Sources/CodexBarCore/Providers/Cursor/CursorAppAuth.swift`, reads the same place), and nothing else of Cursor: no other file, no Keychain item (never "Cursor Safe Storage"), no program. It is opened read-only, without following a link, with one query on the key `cursorAuth/accessToken`, and in a way that creates nothing in Cursor's folder. Brimline first reads the 20 first bytes of the file (the SQLite header, bytes 18 and 19 give the journal mode), then:
  - **classic journal** (the mode of VS Code, which Cursor derives from: its `SQLiteStorageDatabase` runs `PRAGMA journal_mode=WAL` only when its `useWAL` option is true, and nothing in `storageMain.ts` passes it; [`storage.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/base/parts/storage/node/storage.ts), lines 345 to 347): the database is read whether Cursor runs or not, as a read-only opening creates no file in this mode. If a `-journal` file is next to it, a write is going on: nothing is opened and the answer is "busy", tried again later;
  - **WAL**: only while Cursor is running, when both `state.vscdb-wal` and `state.vscdb-shm` already exist, so that SQLite creates nothing; otherwise nothing is opened;
  - anything else in the header (no SQLite header, another version number): "format changed".
- **The one request.** When the value is a plain token (the shape of a JWT, as UTF-8 text or ASCII in UTF-16), `GET https://cursor.com/api/usage-summary` with the cookie of cursor.com's web app, `WorkosCursorSessionToken=<user id>%3A%3A<token>`, the call the dashboard makes for the usage of a plan. **Not documented** by Cursor (its documented APIs are for Enterprise teams, [documentation](https://cursor.com/docs/api)): the public code of CodexBar is the source ([steipete/CodexBar](https://github.com/steipete/CodexBar), commit `5f93dc3`: `CursorStatusProbe.swift` and `CursorStatusProbe+UsageSummary.swift` for the call and the answer, `CursorAppAuth.swift` for the cookie). The user id is the `sub` of the token (the last part after `|`), decoded without checking the signature, with `exp` (an expired token is never sent, with a 60 second margin, and never renewed: Cursor renews it itself when it runs). No other call is made (not the user info, not the team): the address is not read. **This cookie is a full web session of cursor.com**: Brimline sends it to that one address, over HTTPS, and nowhere else; see [SECURITY.md](../SECURITY.md).
- **What you see.** The cycle of the plan as one limit named **Month**, with its percentage and its reset time (the end of the billing cycle). When Cursor gives one or two short words for the plan (`free`, `pro`), they are kept as the `label` of that limit in the JSON for agents (`brimline status --json`, `get_usage`); neither the terminal text nor the panel shows the plan name, and the card is titled just "Cursor". When Cursor gives them, the two model pools show as **Month · Auto** and **Month · API**. The percentages are already points of percent, even under 1 (0.36 is 0.36 %). Without a total percentage, the cents of the plan give it (`used` over `limit`, when the limit is above zero); a team member with no plan block gets the personal cap under `individualUsage.overall` the same way. A plan with no number yet (the start of a cycle) says "No number yet for this period." / "Pas encore de chiffre pour cette période.", never a 0 %. A plan with no cap (`isUnlimited`) says "Cursor sets no limit for this plan." / "Cursor ne fixe pas de limite pour ce plan." Spend on demand, the team's pool and every other key of the answer are ignored.
- **When there is nothing to read** (`not_readable`, reason `protected_sign_in`, in the app, in `brimline status` and in the JSON for agents; no request is made):
  - the value is encrypted (`cursor-safe-storage:` prefix, which Cursor writes for a value protected by its Keychain item), there is no row, or the value is empty, or the database is in WAL mode and Cursor is closed (no `-wal` and `-shm`, so nothing is opened);
  - English: "Cursor protects its sign-in on this Mac: Brimline does not read it. Usage is on cursor.com, Dashboard, Usage."
  - French: "Cursor protège sa connexion sur ce Mac : Brimline ne la lit pas. L'usage est sur cursor.com, Dashboard, Usage."
- **Other states.** An expired token, a refused one (401 or 403) or a redirection (to the sign-in page, never followed) is `expired`: "Open Cursor to refresh the sign-in." / "Ouvrez Cursor pour rafraîchir la connexion." A token whose `sub` is not a plain identifier (letters, digits, `.`, `_`, `-`, 128 characters at most) or that cannot go in a header is never sent: "format changed". A value that is neither a token nor an encrypted value, a file that is not a database or has no `ItemTable`, and an answer that is not the expected one (a page, another JSON, an account whose usage is in a place this reader does not read) are "format changed", never a number. A busy or unreadable database (a `-journal` file next to a classic one included), one that is gone since it was found, a 429 (it waits as long as Cursor asks, one hour at most), another status or no network: unavailable, tried again later with a growing delay; a file of someone else, a link or a file that is not a regular file: refused.
- **State of the check.** The reader was written and tested on databases and answers built by the tests (the schema is VS Code's, [`storage.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/base/parts/storage/node/storage.ts); the key, the prefix, the cookie and the answer are CodexBar's, commit `5f93dc3`; every value is invented), then **tried on 27/10/2026 on a Cursor Free account**: the token was in plain text (no "Cursor Safe Storage" involved), and `brimline status --live` gave the month at 0 %, Auto at 0 % and API at 0 %, resetting on 21 November, a window of 31 days, with the label `free` in the JSON. Ten reads 30 seconds apart gave the same answer, the three files of the database (`state.vscdb`, `-wal`, `-shm`) kept their size and date (the database and its index `-shm` kept their checksum), no file appeared in Cursor's folder, no Keychain prompt came, and the test data were rewritten from the skeleton of that real answer (`brimline status --live --shape --provider cursor`, keys only, invented values). Both journal modes stay handled and tested. **Not compared yet** with the usage page on cursor.com (Dashboard, Usage): it needs a signed-in browser session, and the comparison is pending. A paid plan (Pro, Teams, Enterprise) was not tried, and nothing is claimed for it.

## Gemini, through Antigravity

- **What Brimline does.** When Gemini is on and Google's Antigravity CLI (`agy`) is installed at `~/.local/bin/agy`, Brimline launches Google's official command `agy --print /usage` and reads the text it prints: the limits of each group of models, per window. **This is the one place where Brimline launches another program, and it says so in so many words: Brimline launches the official command `agy --print /usage`; Google's program may then renew its own sign-in. Brimline neither reads nor writes that sign-in.** The sign-in stays in the macOS Keychain, where Antigravity keeps it ([Google's migration page](https://antigravity.google/docs/cli/gcli-migration)); Brimline never asks for it, never signs in for you and makes no request to Google itself.
- **Why this way.** Gemini CLI no longer serves individual Google AI Pro and Ultra plans since 18 June 2026 ([Google's notice](https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals)); Antigravity CLI replaces it. The only source Google documents for the limits of those plans is `/usage` (alias `/quota`) in Antigravity: "a breakdown of your usage limits and remaining requests/tokens for each supported model" ([documentation](https://antigravity.google/docs/cli/commands/usage/)), and in headless mode a command like it prints "a text report" and "uses your cached credentials" ([documentation](https://antigravity.google/docs/cli/headless/)). The Gemini app shows its own limits ([Google's help page](https://support.google.com/gemini/answer/16275805)), but the only known way to read them from outside is with browser cookies, which Brimline never reads.
- **What guards the launch.** Only when Gemini is on and the account is not marked "Do not read". Only the exact path `~/.local/bin/agy` (`PATH` is never searched): a link, a file of someone else, a file the group or others can write, or one that cannot run is refused. Only a build Brimline has verified: the SHA-256 of the binary and the exact text of `agy --version` must both be on Brimline's list of verified builds (one so far: Antigravity CLI 1.4.8, SHA-256 `09fcdd8554e03bed9b2ec936e454c7f115d5610610de09ed7d79fa2feae76940`, seen on 27/10/2026); any other build (Antigravity updates itself) is never launched with `/usage` and the card says "Antigravity was updated: update Brimline." / "Antigravity a été mis à jour : mettez Brimline à jour." (`format_changed`). Fixed arguments, `--print /usage --sandbox`, never an option that skips permissions. A new empty working folder in Brimline's own temporary folder (owner only, removed afterwards), an environment of three variables (`HOME`, `PATH=/usr/bin:/bin`, `LANG=en_US.UTF-8`), nothing typed to the program, 20 seconds then the program is stopped, at most 64 KiB of output, one launch at a time, and in the app, one read every 15 minutes at most (a refresh in between keeps the last numbers; `brimline status --live` in the terminal does not write the cache but reads the app's: it is held to that wait when the app tried less than 15 minutes ago, and launches at once otherwise; making it independent of the cache is a Backlog task).
- **What is read.** The text is read strictly, as data and never as an instruction. As seen on 1.4.8, it has no header line, and each line has four columns separated by tabs: the group (a family of models, such as `Gemini Models` or `Claude and GPT models`, or one model), the name of the limit (`Five Hour Limit Remaining`, `Weekly Limit Remaining`, or a model's own, such as `Gemini 4 Argon Weekly Limit`), a percentage and the reset time in ISO 8601. **The percentage is what remains** (100 % is nothing used): Brimline shows what is used, 100 minus it. Per line, only the group (filtered like every provider's text), the window the name says (`Five Hour`, 5 hours, or `Weekly`, a week), the percentage and the reset time are kept. Every line must have exactly that form: one that does not (a sentence of a model, a percentage out of 0 to 100 or without its `%`, a date that is not valid, three columns, a window Brimline does not know), a control character, a group and window given twice, no line or more than 50 lines is `format_changed` for the whole text, never a number. A non-zero exit or "authentication required" is `expired`: "Open Antigravity to refresh the sign-in." / "Ouvrez Antigravity pour rafraîchir la connexion."
- **Without Antigravity** (`not_readable`, reason `consumer_plan`, in the app, in `brimline status` and in the JSON for agents), the card says the sentence, and nothing is launched:
  - English: "Google does not publish Gemini limits in a form Brimline can read. They are in the Gemini app (Settings, Usage limits) and in Gemini CLI (/stats model)."
  - French: "Google ne publie pas les limites de Gemini sous une forme que Brimline peut lire. Elles sont dans l'app Gemini (Réglages, Limites d'utilisation) et dans Gemini CLI (/stats model)."
  The folder `~/.gemini` and the path of `agy` are only looked for (one `stat` each); nothing inside `~/.gemini` is opened or listed. When Gemini is off (the default), nothing is looked for.
- **What you see.** One limit per group and window ("5 h · Gemini Models", "Week · Claude and GPT models", "Week · Gemini 4 Argon"), with its percentage used and its reset time. On the real try, a window that was not started had a reset time equal to the moment of the reading plus the length of the window (5 hours or a week): `agy` gives no earlier date for it. `--shape` has nothing to show for Gemini, because `agy` prints text and not JSON: `brimline status --live --shape --provider gemini` answers that there is no answer to show. For `best_account`, the account is ranked on the group or model an agent asks for by name; without a name, on its tightest limit.
- **State of the check.** **Read and checked on 27/10/2026, with Antigravity CLI 1.4.8** (SHA-256 on Brimline's list, signature of Google LLC), on the Google account of the maker of Brimline. `agy` does not say which plan that account has: the five limits seen are Gemini Models (5 hours and week), Claude and GPT models (5 hours and week) and Gemini 4 Argon (week), none of them used. What was verified: Brimline reads the same five limits as the text printed by `agy --print /usage --sandbox` launched by hand, with the same reset times to 5 seconds; the real text has exactly the shape of the test data; the answer stayed the same over repeated reads (those inside 15 minutes came from the app's cache, which is how the bound works); no `agy` process stayed behind; no Keychain prompt came; `~/.gemini` was never opened (only looked for); `get_usage` carried no address and no token; and with Gemini turned off, `agy` was not launched at all for more than two minutes. **What is not verified, and is said as it is:** (1) the percentage used (100 minus "Remaining") was seen live at 100 % remaining only, because nothing is consumed on that account; other values are covered by the tests, not by the real account; (2) the reference is the text of `agy --print /usage` itself, not the usage page of Antigravity (Settings), which was not compared; (3) a paid plan (Google AI Pro, Ultra) was not tried, and nothing is claimed for it. Any other build of Antigravity still says "Antigravity was updated: update Brimline." and Brimline launches nothing.

## Grok, through the Grok CLI

- **What Brimline reads.** The Grok CLI's own sign-in file, `~/.grok/auth.json` (the CLI keeps it there, with owner-only permissions: [xAI's authentication guide](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/02-authentication.md)), and nothing else of the CLI: no `config.toml`, no Keychain item, no program launched, and `GROK_HOME`, `GROK_AUTH_PATH` and `XAI_API_KEY` are never read from the environment. The file maps a scope to a sign-in: Brimline decodes only the sign-in with an xAI account (the scope `https://auth.x.ai`, followed by `::` and the OAuth client id), and of it four fields: `key`, `user_id`, `expires_at` and `create_time`. The refresh token, the address, the team, an API key (`xai::api_key`) and the sign-in of any other issuer (an enterprise login) are never decoded.
- **The one request.** `GET https://cli-chat-proxy.grok.com/v1/billing?format=credits` with the session token (`Authorization: Bearer`), the header `X-XAI-Token-Auth: xai-grok-cli` that the proxy needs to tell a user token from a deployment key, and the user id (`x-userid`), the call the Grok CLI itself makes for its credits. **Not documented** by xAI: the CLI's public code is the source ([xai-org/grok-build](https://github.com/xai-org/grok-build), commit `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8`: `crates/codegen/xai-grok-shell/src/extensions/billing.rs` for the call and the answer, `crates/codegen/xai-grok-login/src/model.rs`, `config.rs` and `storage.rs` for the file). xAI's [reference of the CLI](https://docs.x.ai/build/cli/reference) documents no command that gives these numbers.
- **What you see.** One limit per period, with its percentage of the included credits used (`creditUsagePercent`) and its reset time (the end of `currentPeriod`): a week or a month, named by its length (there is no 5 hour window). The older answer (`monthlyLimit` and `used` in cents) is read when the percentage is not there. Credits on demand, the prepaid balance, the history and the plan name in the answer are ignored.
- **No percentage** is never a 0 %. A free account was seen (27/10/2026, Grok CLI 1.0.70) whose answer has a weekly period, `isUnifiedBillingUser` true and zero on demand and prepaid amounts, but no `creditUsagePercent` and no `monthlyLimit`: the card says what is seen, "xAI returns no credit limit for this account." / "xAI ne renvoie aucune limite de crédits pour ce compte.", and says nothing of why or of a number to come. When the answer does give an allowance (`monthlyLimit` above zero) but no use yet (the server leaves out what is zero), the card says "No number yet for this period." / "Pas encore de chiffre pour cette période." When the account uses unified billing (`isUnifiedBillingUser`), the card adds "This limit is a pool shared by the Grok products." / "Cette limite est un pool partagé entre les produits Grok." That pool was not seen on a real account: the free account tried answered no credit limit at all.
- **Never.** An expired session token (`expires_at`, with a 60 second margin; a token with no server expiry is taken to last 30 days from its `create_time`, as the CLI counts) is never sent and never renewed: the CLI renews it itself while it runs, so a Grok CLI left closed for a long time shows "Open the Grok CLI to refresh the sign-in." / "Ouvrez le CLI Grok pour rafraîchir la connexion." The user id goes in a header only if it is letters, digits and `-`, 64 characters at most. Brimline says who it is (`User-Agent: Brimline/<version>`), never the Grok CLI.
- **When there is nothing to read** (`not_readable`, in the app, in `brimline status` and in the JSON for agents):
  - `~/.grok` has no `auth.json`, or none with an xAI account, reason `no_cli`: "xAI only publishes Grok limits for the Grok CLI. Without it, they are in your Grok account settings." / "xAI ne publie les limites de Grok que pour le CLI Grok. Sans lui, elles sont dans les réglages de votre compte Grok." Without a `~/.grok` folder there is no card at all.
  - The Grok CLI is signed in with an API key (`xai::api_key`), reason `api_key`: "The Grok CLI is signed in with an API key: there is no subscription limit to show." / "Le CLI Grok est connecté par une clé d'API : il n'a pas de limite d'abonnement à montrer."
- **Other states.** The sign-in file cut short or empty (the CLI is rewriting it) is a passing failure that Brimline tries again, never "signed out"; a link, a file of someone else or one larger than 1 MiB is refused; a 401 asks to sign in again ("xAI refused the Grok CLI's sign-in: run grok login again."); a 429 waits as long as the provider asks, one hour at most; an answer that is not the expected one (another JSON, a page) is "format changed", never a number.
- **State of the check.** The reader was written on data built from the public code of the Grok CLI, then **tried on 27/10/2026 on a free Grok account** (Grok CLI 1.0.70, signed in through the browser). **xAI returned no credit limit for that account**: the answer has a weekly period, `isUnifiedBillingUser` true and zero on demand and prepaid amounts, but neither `creditUsagePercent` nor `monthlyLimit`. Brimline says exactly that, "xAI returns no credit limit for this account.", shows no gauge and no percentage, and says nothing of why or of a number to come. That is all this try verifies: the shape of the answer (the test data were rewritten from its skeleton, `brimline status --live --shape --provider grok`, keys only, invented values), ten identical reads 30 seconds apart, `auth.json` unchanged, no Keychain call, nothing to agents but the numbers, and the provider turned off stopping every read. **There is no official page or command to compare with**: xAI documents no place that gives these numbers (`grok usage` only gives the tokens of one session), so the only reference is the CLI's own endpoint. What a paid account (SuperGrok, X Premium Plus) answers was **not tried**, and nothing is claimed for it: Brimline may show a percentage there, or the same sentence.
