# Audit de sécurité de Sightglass, 26/10/2026

Premier audit complet du dépôt, avant sa première sortie publique. Commit audité :
`8b66d05094d58d2cdddcd071e05f47d3de9570cd` (version 0.1.0, privée). Audit en lecture seule : code
source, scripts, workflows, historique git, réglages GitHub du dépôt (lecture par l'API), runner de
CI. Aucun test d'intrusion, aucun jeton réel lu.

## Verdict

Aucune faille exploitable aujourd'hui : le dépôt est privé et n'a qu'un collaborateur, et le code
tient ses promesses sur les jetons (lecture seule, en mémoire, un seul hôte, jamais écrit). Une
condition de publication reste ouverte (constat H1) : tant qu'elle n'est pas levée, le dépôt ne doit
pas passer en public. Six constats en tout : une haute, une moyenne, quatre basses.

| # | Gravité | Constat |
|---|---|---|
| H1 | Haute (avant publication) | La CI exécute le code des PR sur le runner du Mac du mainteneur, sous son compte |
| M1 | Moyenne | Masquer un compte n'arrête pas la lecture de son jeton |
| B1 | Basse | Le MCP et la commande exposent plus que des chiffres (adresse, organisation, chemin) |
| B2 | Basse | « Toujours autoriser » sur une invite du Trousseau ouvrirait l'élément à tout processus |
| B3 | Basse | Actions non épinglées par SHA et jeton gardé dans le checkout |
| B4 | Basse (avant publication) | Protections GitHub du dépôt à allumer au passage en public |

## Surface d'attaque

- **Jetons** : lus par `/usr/bin/security find-generic-password -s <service> -w`, nom de service
  calculé, jamais d'énumération ; seuls `accessToken` et `expiresAt` sont décodés
  (`Sources/SightglassCore/Credentials.swift`).
- **Réseau** : un seul point d'accès, `https://api.anthropic.com/api/oauth/usage`, session
  éphémère sans cookie ni cache, redirections refusées, réponse limitée à 256 Kio, URL de la réponse
  vérifiée, 15 secondes au plus (`Sources/SightglassCore/HTTP.swift`).
- **Fichiers écrits** : `usage.json` et `settings.json` (dossier 0700, fichiers 0600, écriture
  atomique avec `O_EXCL | O_NOFOLLOW`), et le LaunchAgent d'ouverture au démarrage
  (`Sources/SightglassCore/Storage.swift`).
- **Entrées** : le serveur MCP sur stdio (lignes bornées à 1 Mio, JSON-RPC écrit à la main, trois
  outils en lecture seule), la commande `sightglass`, les fichiers `.claude.json` des dossiers de
  configuration, la réponse de l'API.
- **CI** : `checks.yml` (push et PR) et `release.yml` (après un `Checks` vert sur `main`), tous deux
  sur `[self-hosted, macOS]`.

## Ce qui a été vérifié et tient

- Aucun appel d'écriture ou de suppression du Trousseau, aucune route de renouvellement de jeton,
  aucun décodage du jeton de renouvellement (recherche dans `Sources/`).
- Le jeton ne sort de la mémoire que dans l'en-tête `Authorization` vers l'hôte fixé dans le code ;
  aucune URL configurable. Un test lit un faux compte de bout en bout et cherche les faux jetons
  dans le cache et dans le JSON des agents (`tests/SightglassCoreTests/CacheAndRankingTests.swift`).
- Le processus `security` est lancé par chemin absolu, avec un tableau d'arguments (pas de shell),
  sortie d'erreur jetée, délai de 60 secondes puis arrêt.
- Les tests ne lisent jamais le vrai Trousseau : le lecteur de jetons et le client HTTP sont
  injectés, le seul test du lecteur réel passe un faux outil.
- Le MCP n'a aucun outil d'action ni de chemin libre ; il lit le cache, jamais le Trousseau. Les
  messages d'erreur ne renvoient que ce que le client a lui-même envoyé.
- Le recul après échec et `Retry-After` sont respectés (pas de rafale sur un point d'accès interne).
- **Dépendances** : aucune dépendance Swift tierce (`Package.swift` sans `dependencies`), scripts
  Python en bibliothèque standard, une seule action tierce (`actions/checkout`), suivie par
  Dependabot. Rien à auditer côté paquets.
- **Historique git** : aucun secret réel ; seuls de faux jetons de test (`sk-ant-...-FAKE-...`).
  Auteurs des commits en adresse `noreply`. Les captures de la documentation sont produites avec
  des comptes fictifs (adresses en @claude.ai).
- Workflows : `permissions` minimales (`contents: read` pour les contrôles, `contents: write`
  seulement pour la release), aucun secret de dépôt, aucune interpolation d'une donnée de PR dans
  un `run:`.

## Constats

### H1 · Haute (condition de publication) · La CI exécute le code des PR sur le Mac du mainteneur

**Preuve** : `.github/workflows/checks.yml:26` et `.github/workflows/release.yml:31`
(`runs-on: [self-hosted, macOS]`). Le runner tourne sous le compte macOS du mainteneur, avec sa
session et son Trousseau de session ouverts. `checks.yml` se déclenche sur `pull_request` et lance
`swift build`, `swift test` et `scripts/build_app.sh`, donc du code choisi par l'auteur de la PR.

**Scénario** : le dépôt passe en public. Une personne ouvre une PR depuis un fork avec un test
Swift qui appelle `/usr/bin/security find-generic-password -s "Claude Code-credentials" -w`
(exactement la technique que l'app documente, et qui ne montre pas d'invite) puis envoie le
résultat sur le réseau. La CI de la PR s'exécute sur le Mac : le jeton du compte Claude, et tout ce
que le compte macOS peut lire (autres éléments du Trousseau, clés, sessions), part chez elle.

**Aujourd'hui** : non exploitable (dépôt privé, un seul collaborateur). Le commentaire de tête de
`checks.yml` le dit déjà, mais `release.yml` ne le dit pas, et rien ne bloque la bascule.

**Correction** (avant tout passage en public) : `runs-on: macos-latest` pour les deux workflows
(gratuité des runners GitHub pour un dépôt public : à vérifier dans la documentation de facturation
de GitHub), ou, à défaut, aucun déclenchement `pull_request` sur le runner auto-hébergé. Régler
aussi « Require approval for all outside collaborators » pour les workflows des forks. Ajouter à
la liste de publication un contrôle : aucun `self-hosted` dans `.github/workflows/`.

### M1 · Moyenne · Masquer un compte n'arrête pas la lecture de son jeton

**Preuve** : `Sources/SightglassUI/AppModel.swift:99` envoie à `UsageService.refresh` la liste
complète `accounts` (ligne 111, tous les dossiers trouvés), sans tenir compte de
`settings.hiddenAccounts`. Un compte masqué voit donc son jeton lu au Trousseau et envoyé à l'API
toutes les 2 à 15 minutes. Les dossiers `~/.claude-*` sont trouvés d'office : aucun réglage ne
permet d'exclure l'un d'eux.

**Scénario** : `SECURITY.md` prévient que l'usage d'un jeton OAuth par une application tierce
peut exposer le compte lu à une mesure d'Anthropic, et invite chacun à juger pour son forfait. Une
personne qui masque un compte professionnel pour ne pas prendre ce risque pense l'avoir retiré ;
Sightglass continue pourtant de lire et d'envoyer son jeton.

**Correction** : ne lire que les comptes visibles (et le dire dans le réglage), ou ajouter un
réglage distinct « Ne pas lire ce compte » ; documenter le comportement dans `docs/accounts.md`.
Test : un compte masqué (ou exclu) ne déclenche aucune lecture du faux lecteur de jetons.

### B1 · Basse · Le MCP et la commande exposent plus que des chiffres

**Preuve** : `SECURITY.md:30` promet « usage numbers only, never a token or a cookie ». Or
`list_accounts` (`Sources/SightglassCore/MCPServer.swift:167-172`), `get_usage` et
`sightglass status --json` (`Sources/SightglassCore/AgentReport.swift:47-50`) rendent l'adresse
e-mail, l'organisation et le chemin absolu du dossier (qui contient le nom du compte macOS) ;
`sightglass accounts --json` y ajoute le nom de l'élément du Trousseau.

**Scénario** : un agent branché sur le MCP, quel que soit son fournisseur de modèle, envoie ces
données personnelles à ce fournisseur à chaque appel. Rien de secret, mais plus que ce que la
politique annonce.

**Correction** : corriger la phrase de `SECURITY.md` (les réponses portent adresse, organisation
et dossier, jamais de jeton) ; rendre le dossier sous la forme `~/...` plutôt qu'en chemin absolu ;
envisager un réglage qui masque les adresses dans les sorties pour agents.

### B2 · Basse · « Toujours autoriser » ouvrirait l'élément du Trousseau à tout processus

**Preuve** : `docs/install.md:32` et `docs/accounts.md:68` disent seulement « lire l'invite avant
d'autoriser ». Le choix de `/usr/bin/security` plutôt que du framework Security est assumé et
justifié (`SECURITY.md`, `Credentials.swift`).

**Scénario** : sur une installation où `security` n'est pas déjà dans la liste d'accès de
l'élément, macOS montre une invite à chaque lecture (toutes les quelques minutes). La personne
finit par cliquer « Toujours autoriser » : `/usr/bin/security` entre dans la liste d'accès, et tout
processus du compte lit alors le jeton sans invite. Comportement de la liste d'accès du Trousseau
à vérifier dans la documentation d'Apple avant de l'écrire tel quel.

**Correction** : dire dans `docs/accounts.md` et `docs/install.md` ce qu'implique « Toujours
autoriser » pour l'outil `security`, et recommander « Autoriser » ou « Refuser » ; au refus,
l'app affiche déjà le compte comme indisponible.

### B3 · Basse · Actions non épinglées par SHA et jeton gardé dans le checkout

**Preuve** : `actions/checkout@v4` (`checks.yml:29`, `release.yml:34`) ; réglage du dépôt
`allowed_actions: all`, `sha_pinning_required: false`. `actions/checkout` garde par défaut le
jeton du job dans `.git/config` du dossier de travail (`persist-credentials`), y compris le jeton
`contents: write` du job de release, sur un runner qui garde ses dossiers entre deux jobs.

**Correction** : épingler `actions/checkout` sur un SHA complet (Dependabot sait les tenir à
jour), `persist-credentials: false` dans les deux workflows (la release passe par `gh` avec
`GH_TOKEN`, sans `git push`), et n'autoriser que les actions de GitHub dans les réglages du dépôt.
La PR Dependabot ouverte vers `actions/checkout` v7 est l'occasion de le faire.

### B4 · Basse (au passage en public) · Protections GitHub du dépôt à allumer

**Preuve** : lecture de l'API du dépôt : protection de branche et règles indisponibles en dépôt
privé gratuit (403), `security_and_analysis` vide. `SECURITY.md` renvoie vers le signalement privé
de vulnérabilités, qui n'est pas encore actif.

**Correction** (le jour de la bascule, dans les réglages du dépôt) : règle de protection de
`main` (PR obligatoire, contrôle `Checks` requis, pas de force push), signalement privé des
vulnérabilités, analyse des secrets avec protection au push, alertes Dependabot. Ajouter une
recherche de secrets (gitleaks ou équivalent) aux contrôles de texte.

## Suivi des avis précédents

Le conseil de sécurité du cadrage (octobre 2026) avait posé des conditions ; leur état au commit
audité :

| Condition | État |
|---|---|
| Runner auto-hébergé interdit pour un dépôt public | Ouvert : constat H1 |
| Les tests ne touchent jamais le vrai Trousseau | Tenu |
| Un test cherche les jetons dans les sorties | Tenu (cache et JSON des agents) |
| MCP en lecture seule, sans Trousseau | Tenu |

| Option qui masque les adresses dans les sorties pour agents | Ouvert : constat B1 |
| Respect de `Retry-After`, pas de rafale | Tenu |

## Hors périmètre

Un logiciel malveillant qui tourne déjà sous le compte de la personne lit les mêmes éléments que
Sightglass (`SECURITY.md`, modèle de menace). La conformité aux conditions d'Anthropic reste une
question de produit, suivie à part.
