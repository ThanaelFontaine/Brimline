# Security policy

Brimline reads the sign-in tokens of your AI tools (for Claude Code, from the macOS Keychain; for Codex, Grok and Cursor, from a file each of them keeps) and, for Gemini, launches Google's own command instead of reading a token. Security reports are taken seriously and handled privately.

## Reporting a vulnerability

**Please do not open a public issue for a security problem.**

Use GitHub's private vulnerability reporting: on the repository page, **Security** tab, **Report a vulnerability**. If the button is not there, contact the maintainer privately through the contact details on their GitHub profile.

Please include what an attacker can do and under which conditions, steps to reproduce, and the affected version and macOS version. Never send real tokens or account data in a report: use fictitious data.

What to expect: an acknowledgement within 7 days, an assessment and a plan, then a fix released as a new version with a changelog entry. Brimline is maintained on a volunteer basis, so timelines are best effort.

## Supported versions

Only the latest released version receives security fixes.

## Threat model

### What Brimline is

A macOS app that runs under your user account. It reads the tokens your AI tools already store, asks each provider for the usage of each account, and shows the result in the menu bar, in a command with JSON output and in a local MCP server. There is no Brimline server and no telemetry.

### What it promises

- **Read only.** Tokens are read, never refreshed, rewritten, moved or copied to another store. Refreshing a token can rotate it, which may sign the official tool out: Brimline never does it. **The one exception is Gemini, and it is said in so many words below:** Brimline launches Google's command `agy --print /usage`, and Google's program may then renew its own sign-in; Brimline itself reads and writes nothing of it.
- **Tokens stay in memory**, only for the request that needs them. They are never written to a log, a cache file, the JSON output or the MCP answers.
- **Only the providers' own hosts** are contacted, over HTTPS, and only with the account's own token (for Gemini, Brimline contacts no host: it launches Google's program, which does what it does). Each reader has a closed list of URLs, compared whole (host, path and query); anything else is refused before the request leaves, redirections are refused, and no cookie is kept. None is sent either, except the session cookie of cursor.com that the Cursor reader needs (see the Cursor section below).
- **A provider is read only if you turned it on.** Claude is on, as it always was; every other provider starts off (see below).
- **The local MCP server and command expose usage numbers only**, never a token or a cookie.

### Every place Brimline looks at, in one table

Detail and reasons are in the sections below; this table is what the code does, and a test or a check covers each row (`ConsentTests`, `SecretFileTests`, `HTTPAllowListTests`, the launcher tests and `LeakTests`).

| Provider | What Brimline looks at | What it opens | What it launches | The one request |
|---|---|---|---|---|
| Claude | `~/.claude`, each `~/.claude-*` folder and the folders you add, and the names in Brimline's own `claude-reports` folder | `.claude.json` of the folder (identity), one Keychain item per folder, and the Claude Code report of an address (Brimline's own file, no secret in it) | Apple's `/usr/bin/security`, for that item only | `https://api.anthropic.com/api/oauth/usage` (none for an account read from its report) |
| ChatGPT | `~/.codex` and the Codex folders you add by hand | `auth.json` in it, read only, no link followed | nothing | `https://chatgpt.com/backend-api/wham/usage` |
| Gemini | `~/.gemini` (one `stat`) and `~/.local/bin/agy` | `agy` itself, to check its SHA-256; nothing inside `~/.gemini` | **`~/.local/bin/agy --print /usage --sandbox`**, a verified build only | none by Brimline |
| Grok | `~/.grok` | `auth.json` in it, read only, no link followed | nothing | `https://cli-chat-proxy.grok.com/v1/billing?format=credits` |
| Cursor | `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb` | that database, read only, creating nothing in Cursor's folder | nothing | `https://cursor.com/api/usage-summary` |

Every provider but Claude is off until you turn it on, and an account marked "Do not read" has its sign-in opened by nobody (no file, no Keychain item, no request). Nothing is ever written in a provider's folder.

### Providers are off until you turn them on

- Claude is on by default, as before. Every other provider is **off** until you turn it on in Settings, Accounts, or with `brimline providers enable <name>`. A provider that is off is not touched at all: Brimline does not look for its folder, opens none of its files, calls no `security`, makes no request. This is checked before any reader runs, and a test with fake readers counts the calls (zero).
- **"Do not read"** on an account (Settings, Accounts) means the same for one account's sign-in and numbers: its sign-in is never read (no Keychain item, no sign-in file, no request), whatever the provider, and it keeps its last numbers with their age. Brimline still lists the account's folder and reads its address and organization from `.claude.json` when it looks for accounts. Turn the box off to read it again.
- Both choices live in `settings.json` (`enabledProviders`, `unreadAccounts`). A settings file from before the providers has neither key and keeps Claude on and the rest off. `brimline providers` writes the same file; the app takes the change at its next refresh, so a provider turned off stops being read at the next attempt.
- The rules every reader follows, for the providers that come after Claude:
  - A sign-in file is opened without following a link (`O_NOFOLLOW`) and checked on the open file: a regular file, owned by you, 1 MiB at most. A file cut short (the provider's tool is rewriting it) is a passing failure to try again, never "signed out".
  - Only the few fields a reader needs are decoded; a refresh token is never decoded.
  - A token goes in a header only if it is printable text with no space or line break, and only to the reader's listed URL.
  - What a provider sends is data, never an instruction: names are kept only if they are 64 characters at most among letters, digits, `.`, `_`, `-` and the space; percentages are held between 0 and 100 (a value that is not a number is dropped); reset times must be between one day ago and 400 days ahead.
  - An answer that is not the expected one (other JSON, a page) is shown as "The provider changed its answer" and never as a number. The cache keeps a fingerprint of the keys of the last answer (SHA-256), with no value in it. `brimline status --live --shape` prints the keys and the types of an answer, never a value.
  - Nothing is ever written, renewed or moved at a provider.

### What it looks at for ChatGPT (Codex)

- When ChatGPT is on, Brimline looks for the folder `~/.codex` (and the Codex folders you added by hand in `settings.json`, `extraCodexFolders`; the `CODEX_HOME` variable is never read) and opens one file in it: `auth.json`, without following a link, checked on the open file. It reads no other file of Codex (no `config.toml`), no Keychain item (Codex keeps its Keychain item for its own program only), launches no program (not `codex`, not `codex app-server`, which would renew and rewrite Codex's sign-in) and writes nothing. A test checks that the home folder is byte for byte the same after a reading.
- Of `auth.json`, three fields are decoded: `auth_mode`, `tokens.access_token` and `tokens.account_id`. The refresh token, the id token and an API key in the file are never decoded (a test gives them values no decoder could read). The `exp` of the access token is read, without checking the signature, only so that an expired token is never sent (with a 60 second margin); it is never renewed.
- The token and the account id go only to `https://chatgpt.com/backend-api/wham/usage`, over HTTPS, and only if they are printable text with no space or line break (the account id: letters, digits and `-`, 64 characters at most). The request is a read of the usage that consumes no quota. Brimline says who it is (`User-Agent: Brimline/<version>`), never Codex.
- The address and the plan in Codex's files and in the answer are not kept. Tests plant fake tokens, a fake account id and a fake answer secret, and look for them in the cache, the settings, the JSON of the command and the MCP answers (none).

### What it looks at for Gemini (the one third-party program Brimline launches)

- **The rule lifted, in so many words:** for Gemini, Brimline launches the official command `agy --print /usage`; Google's program may then renew its own sign-in. Brimline neither reads nor writes that sign-in (it is in the Keychain, where Antigravity keeps it; Brimline reads no item of it). No other provider launches a third-party program: Claude is read through Apple's own `/usr/bin/security` tool, a read of one Keychain item, and ChatGPT and Grok through one request each.
- **Only when Gemini is on**, the account is not marked "Do not read", and `~/.local/bin/agy` is there. When Gemini is off, nothing is looked for. Brimline checks that `~/.gemini` is a folder and that `agy` is at its path (one `stat` each) and opens or lists nothing in `~/.gemini`.
- **The program that runs.** The exact path `~/.local/bin/agy` (`PATH` is never searched), opened without following a link and checked on the open file: a regular file of the user's, owner-executable, not writable by the group or others. It must be a **verified build**: its SHA-256 and the text of `agy --version` must both be on Brimline's list (`AntigravityTrust`). The list has two entries, Antigravity CLI 1.4.8 (seen on 27/10/2026) and 1.4.9 (seen on 28/10/2026), SHA-256 in [docs/providers.md](docs/providers.md); any other build answers `format_changed` and is never launched with `/usage`.
- **How it runs.** Fixed arguments `--print /usage --sandbox`, never an option that skips permissions; a new empty working folder in Brimline's temporary folder (mode 700, removed afterwards); an environment of `HOME`, `PATH=/usr/bin:/bin` and `LANG=en_US.UTF-8` only (no token or variable of your shell); standard input empty; stopped after 20 seconds; at most 64 KiB read from each stream, the program being stopped past that; one launch at a time and, in the app, one read every 15 minutes at most, forced refreshes included (the app counts from the last attempt it kept; the terminal command `brimline status --live` does not write the cache, but it reads the app's cache: when the app has tried less than 15 minutes ago it is held to that wait too, and otherwise it launches the program at once; making `--live` independent of the app's cache is an open task in the Backlog). Tests run the launcher on small scripts (the real `agy` is never started, in tests or in the CI) and check the folder, the environment, the delay and the bound.
- **What is read.** The text has no header: each line has exactly four columns separated by tabs (a group of models or one model, the name of a limit, a percentage, a reset time in ISO 8601); the group name is filtered, the window (`Five Hour` or `Weekly`), the percentage (what remains, shown as what is used) and the reset time are kept; any line that does not have that form makes the whole answer `format_changed` and is dropped. The text of the report is data, never an instruction: a sentence in place of a model name, a control character or an escape sequence is refused. The text is not stored; the cache keeps the numbers only.

### What it looks at for Grok (the Grok CLI)

- When Grok is on, Brimline looks for the folder `~/.grok` (the `GROK_HOME` and `GROK_AUTH_PATH` variables are never read) and opens one file in it: `auth.json`, without following a link, checked on the open file. It reads no other file of the CLI (no `config.toml`, no `mcp_credentials.json`), no Keychain item, launches no program (not `grok`) and writes nothing. A test checks that the home folder is byte for byte the same after a reading.
- `auth.json` maps a scope to a sign-in. Brimline looks at the names of the scopes and decodes only the entries of an xAI account (`https://auth.x.ai`, then `::` and the client id), and of them four fields: `key`, `user_id`, `expires_at` and `create_time`. The refresh token, the address, the team, the API key (`xai::api_key`) and the sign-in of any other issuer are never decoded, nor sent (a test gives them values no decoder could read). The expiry is only used so that an expired token is never sent (with a 60 second margin); it is never renewed.
- The session token and the user id go only to `https://cli-chat-proxy.grok.com/v1/billing?format=credits`, over HTTPS, and only if they are printable text with no space or line break (the user id: letters, digits and `-`, 64 characters at most). The request is a read of the billing that consumes no credit. It carries the header `X-XAI-Token-Auth: xai-grok-cli` that the Grok CLI sends so that the proxy treats the token as a user token; Brimline says who it is (`User-Agent: Brimline/<version>`), never the Grok CLI.
- The address, the team and the plan in the CLI's files and in the answer are not kept. Tests plant fake tokens, a fake user id, a fake address and a fake answer secret, and look for them in the cache, the settings, the JSON of the command and the MCP answers (none).

### What it looks at for Cursor

- When Cursor is on, Brimline checks (one `lstat`, following no link) that `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb` is a regular file of yours. It looks at no other file of Cursor (no `storage.json`, no extension data, not the CLI's folder), reads no Keychain item (never "Cursor Safe Storage", the key that opens everything Cursor encrypts) and launches no program. The only request is the one described below.
- It first reads the 20 first bytes of that file (the SQLite header, through a descriptor opened read-only that follows no link) to learn the journal mode, and creates nothing in Cursor's folder in either mode. In the classic journal mode (the one VS Code uses, and so, most likely, Cursor), a read-only opening creates no file, so the database is read whether Cursor runs or not, unless a `-journal` file is next to it (a write in progress): then nothing is opened and the answer is "busy". In WAL mode, the database is opened only while Cursor is running: both `state.vscdb-wal` and `state.vscdb-shm` must already exist, as regular files of yours, otherwise nothing is opened (SQLite could create them, which would be a write in Cursor's folder). The opening is `SQLITE_OPEN_READONLY` on a `mode=ro` URI, refuses a link as the file, and is never `immutable=1` (it would ignore a token still in the log or in a journal) nor a copy on disk. SQLite touches the shared-memory index `-shm` as any WAL reader does; tests check, in both modes, that the database and its log do not change by a byte or a date, and that no file appears.
- One prepared query: `SELECT value FROM ItemTable WHERE key = ?` with the key `cursorAuth/accessToken`. The value is classified (an encrypted value, a plain token shaped like a JWT, nothing, or something else). Only a plain token is used: it stays in memory for the one request below and is dropped with it; it is not kept, not written in the cache, the settings, the answers to agents or the logs. A value that Cursor encrypted is never decrypted.
- The token is a JWT, decoded without checking its signature for two claims only: `exp` (an expired token is never sent, with a 60 second margin, and never renewed) and `sub`, whose last part after `|` is the user id. The user id must be letters, digits, `.`, `_` or `-`, 128 characters at most, and the token must be printable text with no space or line break, 4096 characters at most: otherwise the token is not used and nothing is sent, so that nothing in the token can shape the header.
- **The cookie.** The token and the user id go only to `https://cursor.com/api/usage-summary`, over HTTPS, as the cookie `WorkosCursorSessionToken=<user id>%3A%3A<token>` of cursor.com's web app, because that is how the call the dashboard makes for the usage of a plan is authenticated. **That cookie is worth a full web session of cursor.com**, not only the usage: this is the one place where Brimline sends a credential that gives more than a read of the usage, and it is the reason the provider is off until you turn it on. Brimline sends it to that one address and nowhere else (the address is a closed list: no other path, no query, no other host), with an ephemeral session that sends and keeps no other cookie and no cache, a 15 second timeout, and no redirection followed (a redirection means the sign-in page: the card asks to open Cursor). The answer's `Set-Cookie` is never kept. It carries `User-Agent: Brimline/<version>` and says who it is, never the Cursor app. No other Cursor address is called (not the user info, not the team): the address of the account is not read, and neither is the plan's spend on demand.
- The answer is data, never an instruction: only the cycle dates, the percentages and the cents of the plan are decoded; the plan name is kept only when it is one or two short words; every other text of the answer is ignored. The shape of the answer (`brimline status --live --shape`) writes a key that could be data (an address, an id, a UUID, a number) as `<key>`. Tests plant a fake token, a fake refresh token, a fake address, a fake `Set-Cookie` and a hostile answer, and look for them in the cache, the settings, the JSON of the command and the MCP answers (none).

### How it reads Claude Code sign-ins

- Claude Code keeps each sign-in in the macOS Keychain, one generic password per configuration folder. Brimline computes the item's exact service name from the folder (`Claude Code-credentials`, or `Claude Code-credentials-` followed by the first 8 hex digits of the SHA-256 of the folder's absolute path) and asks for that one item. It never lists or searches the Keychain.
- The read goes through Apple's `/usr/bin/security find-generic-password -s <service> -w`, whose output is piped straight into the app's decoder: it is never printed, logged or stored. Only `accessToken` and `expiresAt` are decoded; the refresh token is never decoded, stored or used.
- If `security` does not answer within 60 seconds, it is stopped and the account is shown as unavailable.
- Why the `security` tool rather than the Keychain framework: in our tests, reading Claude Code's items with that tool showed no prompt, which suggests it is already allowed to read them (to be confirmed on other setups). An app reading them directly is not on their access list, so macOS would ask for each item, and ask again after each rebuild of an app signed ad hoc, which would train people to click "Always Allow" without reading.
- The token is sent only to `https://api.anthropic.com` (the usage endpoint Claude Code uses), over HTTPS, with an ephemeral session that keeps no cookie and no cache. Requests time out after 15 seconds. Each request carries the token (`Authorization: Bearer`), the header `anthropic-beta: oauth-2025-04-20`, and `User-Agent: Brimline/<version> (+https://github.com/ThanaelFontaine/Brimline)`: Brimline says who it is and never presents itself as Claude Code.
- An expired token is reported as "Session expired": Brimline does not ask for usage with it and does not renew it.

### What it writes

- `~/Library/Application Support/Brimline/usage.json` (the last numbers, statuses, addresses and folders of the accounts, and a fingerprint of the keys of each answer) and `settings.json` (preferences, the providers that are on, the accounts marked "Do not read"), in a folder readable by your user only (`0700`, files `0600`). The cache type has no field for a token, and a test writes a cache from fake tokens and checks none of them is in the file.
- `~/Library/Application Support/Brimline/claude-reports/`, only through `brimline report claude`: one report of numbers per address (see "Claude Code reports" above), folder `0700`, files `0600`.
- `~/Library/LaunchAgents/eu.thanaelfontaine.brimline.plist`, only when you turn on "Open at login"; it opens the app and nothing else.
- Nothing in the Keychain, nothing in the Claude Code folders.
- Hiding menu bar icons: a private API, the Accessibility permission, and what they read. With "Hide without removing" on (Settings, Menu Bar, off by default), Brimline adds one more item of its own to the menu bar, a thin bar. On macOS 27 and later, when macOS has its allow-list of the menu bar (the private framework `MenuBarClientCore`, classes `MBAssessmentModeConfiguration` and `MBAssessmentModeAssertion`, which Apple does not document), Brimline hides with it: it uses that private API, and the Accessibility permission, which macOS asks for the first time; up to 0.3.0, Brimline is signed ad hoc, so the grant covers one build (it names its cdhash), and a new build (an update) is no longer covered until the permission is given again; Brimline then says so in its window and in Settings. From the next version, the release is signed with Brimline's own self-signed certificate ("Brimline Code Signing", SHA-1 `28E5BDC0D2C3E5EEFD43C9C42FEAE493167F47B4`), so the grant names that certificate and should cover the next builds (to be checked on a real Mac before that release). The risk that comes with it: whoever holds the private key of that certificate can sign an app with the identifier `eu.thanaelfontaine.brimline` that inherits the Accessibility permission given to Brimline, and a self-signed certificate cannot be revoked. The key lives only in two secrets of the release workflow and in the maintainer's keychain; a build from the source without it is ad hoc. It reads with that permission only the positions of the icons of the other open apps in the menu bar (the `AXExtrasMenuBar` attribute), to know which are left of the bar; it reads no window, no text, no content of the other apps. It writes one thing: `shownApps`, the bundle identifiers of the apps found right of the bar the last time, in its own `settings.json`. It writes in no file of macOS or of another app; macOS itself keeps the place of the bar, as for every item you drag. Without the allow-list (macOS 26 and before, or a macOS that removed it), Brimline only changes the length of its own item: no permission, no private API. See [docs/menu-bar.md](docs/menu-bar.md) for what was tried and its limits.
- Once, at its first launch, it reads `settings.json` and `usage.json` from the old folder in `~/Library/Application Support` (the one named after the old app) and copies them to the Brimline folder: a real folder owned by you, files opened without following a link, regular, owned by you, 1 MiB at most, decoded into the same types as above and written again (so no token can come over), never over an existing file. The old folder is not changed.

### Claude Code reports (`brimline report claude`)

- **What goes in.** The command reads its standard input: the JSON Claude Code gives a status line command (`--statusline`), or the output of `claude -p --output-format stream-json`. Of the status line JSON it decodes `rate_limits.five_hour` and `rate_limits.seven_day` only, and of them `used_percentage` and `resets_at`; of stream-json, only the lines whose `type` is `rate_limit_event`, and of them `rate_limit_info.unifiedWindows.five_hour` and `.seven_day`, `utilization` and `resetsAt` only. Every other line and key (the session, the messages, the tool results, anything that could hold a token) is skipped. The input is read in blocks of 64 KiB: a line longer than 64 KiB is dropped as it comes, never held whole, and only the lines whose `type` is `rate_limit_event` are decoded (a message that merely quotes the word is not), each one on its own, its objects freed before the next, so memory stays bounded however long the stream; with `--statusline`, an input over 1 MiB is not kept. The input is always read to its end, a wrong option included, so that the program writing into the pipe (`claude -p`) never finds it closed (`EPIPE`); an input that program left non-blocking (`O_NONBLOCK`) is waited on, never taken as ended, and its flag is not changed.
- **What is kept.** A report has a closed type: a version number (`schema_version`), the address (lower case, a plain address checked character by character, 200 characters at most, so it can name the file, its lock and its temporary file), the source (`statusline` or `stream-json`), the time, a status (`ok` or `format_changed`) and the two windows (share used held between 0 and 100, reset time in seconds between 2020 and 400 days ahead, the time each was seen). No field of it can hold a text from the input. `LeakTests` plants a fake token in every place of a stream and of a status line JSON, and looks for it in the report, the cache, the JSON of the command and the MCP answers (none).
- **Where.** `~/Library/Application Support/Brimline/claude-reports/<address>.json`: the folder is refused if it is a link, someone else's, or open to other users (an existing folder is never changed: `--dir ~` is refused, not turned to `0700`), the missing folders are created `0700`, each file written atomically (`O_EXCL`, `0600`, synced, renamed), under an advisory lock per address so that two sessions do not lose a window. Nothing is written in a Claude Code folder.
- **How it is read.** The app lists the names of that folder (a regular file of yours whose name is a plain address; no link). A report is opened without following a link, checked on the open file (regular, yours, 64 KiB at most), decoded into its type, and used only if the address inside is the one of its name. A report in another form is "format changed", never a number.
- **Consent.** Reports are read only while Claude is on, and the report of an account marked "Do not read" is not opened. The mark is also kept by address (`claude:report:<address>` in `unreadAccounts`): the report of that address stays closed for every account, even when the folder's `.claude.json` loses its address for a while, and an account known by its report has an id made of its address only. "Do not read" does not stop the command: it keeps writing the report until it is taken out of the status line. An account with a folder keeps its direct reading: its report is used only when the session has expired or the Keychain item is missing, and only if it is newer than the numbers last read from Anthropic.
- **The status line.** With `--statusline` the command reads no setting, no cache and no Keychain item, never writes on the error output and always exits 0 (Claude Code shows an empty status line for a command that fails or prints nothing). It prints at most one line of numbers, and only when its input gave limits. With `--account auto` it reads one more file: the `.claude.json` of the folder in use (`CLAUDE_CONFIG_DIR`, or `~/.claude.json`), opened without following a link, the user's own regular file of 16 MiB at most, of which only `oauthAccount.emailAddress` is decoded; and it writes and shows nothing unless the input's `transcript_path` is an absolute path, with no `.` or `..`, under `<that folder>/projects/` (otherwise the numbers may belong to another account): a missing, empty or relative `transcript_path`, or one that is not a text, is refused. The paths are compared as written and with their links resolved, a transcript not created yet through the folders above it that exist.
- **A report is not authenticated.** Any program running as you can write one: it can change the numbers shown and the choice of `best_account`, never read a token (a report holds none, and Brimline sends nothing because of one).
- **What is not documented.** `unifiedWindows` is not in the published type of `rate_limit_event` (it was seen on the Claude Code versions of October 2026): when it is missing, the report says "format changed" and no number is guessed. The status line fields are documented ([statusline](https://code.claude.com/docs/en/statusline)).

### Anthropic's terms

Anthropic's documentation restricts the use of Claude.ai OAuth tokens by third-party applications ([Authentication and credential use](https://code.claude.com/docs/en/legal-and-compliance)). Brimline reads the user's own token on the user's own Mac, read only, never writes or renews it, sends it only to Anthropic and announces itself under its own name. It is not an official or endorsed Anthropic product, and we make no claim that this use is permitted: each user judges for their plan. The same page says Anthropic may enforce these restrictions without prior notice, which is a risk for the account that is read. See the README.

### Out of scope

Malware already running under your user account can read the same Keychain items and files as Brimline (macOS may ask your permission the first time an app reads a Keychain item it was not allowed to read). Brimline does not try to defend against it.
